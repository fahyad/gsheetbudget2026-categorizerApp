## ⚠️ READ THIS BEFORE TOUCHING APPS SCRIPT

**Apps Script lives at `apps-script/Code.js`** (managed via [clasp](https://github.com/google/clasp)). Edit there, not in the Apps Script editor.

**To deploy a change, ALWAYS use:**

```bash
# From the user's laptop only (clasp auth lives in ~/.clasprc.json):
deploy "vNN — short description"
```

The `deploy` shell function is installed in `~/.zshrc` and defined by `scripts/deploy-alias.sh` in this repo. It does:

1. `cd ~/gsheetbudget2026-categorizerApp && git pull`  (gets commits any Claude session pushed from elsewhere)
2. `cd apps-script && ./deploy.sh "$@"`  (runs `clasp push` + `clasp deploy -i $PROD_ID`; pre-deploy guard blocks if Code.js has uncommitted substantive changes)
3. Auto-commits the post-deploy timestamp bump and pushes back to origin (so production stays reproducible from git)

If the function is missing on a new machine, install with: `cat ~/gsheetbudget2026-categorizerApp/scripts/deploy-alias.sh >> ~/.zshrc && source ~/.zshrc`. Falls back to running the steps manually if the function isn't installed.

### Why deployment requires the user's laptop (not Claude-in-the-cloud)

`clasp` authenticates per-machine via `~/.clasprc.json` — an OAuth token tied to the user's Google account. The token is generated by running `clasp login` once, stored on that machine, and is **deliberately not in the repo**. Claude environments running in sandboxes (claude.ai/code on the web, GitHub-hosted Claude, etc.) don't have this token, so they cannot deploy. They can edit + commit + push code; the user runs `deploy "..."` on their laptop. **This is a feature, not a missing capability** — the boundary prevents anyone with repo write access from deploying code that runs as the user (i.e., that reads the user's Gmail). Don't try to "fix" this by adding service-account credentials to GitHub Actions; the friction is the security model.

**NEVER use plain `clasp deploy`** — it creates a new deployment with a new URL. The PWA is hardcoded to one URL. Plain `clasp deploy` silently breaks production.

```bash

#   3. Apps Script editor → Project Settings → Script Properties → API_KEY
KEY="<paste-api-key-here>"

# List all tabs + dimensions
curl -sL "${URL}?action=dumpSheet&apiKey=${KEY}&metadata=true" | python3 -m json.tool

# Read a specific tab/range (display values — formatted strings)
curl -sL "${URL}?action=dumpSheet&apiKey=${KEY}&tab=Setup&range=A1:E27" | python3 -m json.tool

# Read with formulas instead of values (debugging formulas)
curl -sL "${URL}?action=dumpSheet&apiKey=${KEY}&tab=Budget&range=D2:D10&includeFormulas=true" | python3 -m json.tool
```

Caps at 10000 cells per request. Read-only (no writes). API-key gated.

Tabs in this sheet (v11.13+): `Instructions`, `Logs`, `ClientMetrics`, `Setup`, `Fixed Monthly Expenses`, `Budget`, `Transactions`, `Saving`. `ClientMetrics` auto-creates on first PWA flush — do not rebuild manually.

**Pending tab REMOVED in v11.0** — single-ledger architecture. The Transactions tab now holds:
- All categorized transactions (manual + email-parsed + PWA-categorized)
- All UNCATEGORIZED transactions (Category column empty = "needs categorization")

PWA reads Transactions where Category="" AND Timestamp is set. Categorize action updates the Category cell of an existing row. No copy/move between tabs.

**Transactions tab layout (v11.0+):** 8 columns:
- A: Date | B: Merchant | C: Amount (signed) | D: Category (empty = uncategorized)
- E: Main Category (formula from D + Setup) | F: Transaction # (manual) | G: Period (formula from A + PayPeriods)
- H: Timestamp (NEW in v11.0 — precise datetime from email; blank for manual entries)

**Categorization rule:** PWA only sees rows where `Category=""` AND `Timestamp` is set. Manual rows (Timestamp blank) are invisible to PWA — by design, they're already categorized.

**Saving tab layout (v11.11+):** 9 columns A-I, dashboard at rows 1-3, header at row 5, goals at rows 6-105 (up to 100 goals).
- A: Goal Name | B: Linked Category (dropdown) | C: Target | D: Target Period (dropdown)
- E-H: computed (Currently Saved, Allocated This Period, Periods Remaining, Needed Future Periods — all currency/integer, no CF)
- I: Notes
- Dashboard B3 has the "current period" INDEX+MATCH (match_type=1) that all per-row formulas reference. Don't move it; don't replace with XLOOKUP-over-multiplied-booleans (see trip-up #11).
- Column H's "Needed Future Periods" is adaptive: when F (Allocated This Period) > 0, divides by (G - 1) so the value stays constant when user budgets the previously-shown amount. When F = 0, divides by G. Previous static formula caused confusing user-facing drift from $222 → $209 after allocation.
- Tab gets created automatically by Update Script if missing — no migration step needed.

**Budget tab layout (v10.5+):**
- **Rows 1-6:** Dashboard (display only). B1 = period dropdown. Row 4 shows Net Income / Fixed Expenses / Total Budgeted / Ready to Assign for the selected period. F1 shows period progress ("Day X of Y").
- **Row 7:** Header row (Period | Main | Category | Budgeted | Spent | Available)
- **Rows 8+:** Category data (no more `_income` rows). 8 categories × 26 periods = 208 data rows.
- **Frozen rows:** 7 (dashboard + header always visible when scrolling)
- **Slicer:** to the right of column F (anchored row 1 col 8). Filters by Period (col 1 of data range). Independent of dashboard dropdown.
- **Named ranges** (Budget_Period, Budget_Category, Budget_Budgeted, Budget_Available) all start at row 8.

## PWA architecture (v0.12 → v0.15.3)

Restructured in v0.12 from a 657-line single-file app into a thin shell + lazy-loaded view modules. The shell is ~40 LOC and loads instantly; each view is fetched on first navigation. v0.13 filled the dashboard; v0.14 added the Auto sub-tab; v0.15 reskinned the whole app in "Minimal Monochrome" per a Claude Design handoff; v0.15.3 added a client-side metrics pipeline feeding a new `ClientMetrics` sheet tab.

**Module layout:**
```
js/
  app.js           ~40   shell: version label, initial-route gate, beforeunload
  router.js       ~100   hashchange -> lazy import(view) -> mount(root) / unmount(); owns tab-bar active-class + Categorize pending-count badge + mount-timing events
  ui.js            ~25   shared showError / showSuccess only
  config.js        ~40   APP_VERSION, DEFAULT_API_URL, localStorage getters
  api.js           ~80   request() + endpoint wrappers; every request goes through lib/metrics.recordStart/recordComplete
  store.js        ~155   in-memory + localStorage state (txns, categories, syncQueue)
  periods.js      ~125   bi-weekly pay-period math (currentPeriod, periodForTimestamp, allPeriods)
  lib/
    budget.js     ~200   dashboard data layer: dumpSheet(Budget) + dumpSheet(Saving), parseCurrency, formatCurrency, 10-min cache, invalidateDashboardCache; emits cache-hit/miss metric events
    suggest.js    ~175   merchant normalizer + frequency index from Transactions; suggest() ≥70% confidence; emits cache-hit/miss events
    swipe.js       ~95   vanilla touch factory attachSwipe(translateEl, { revealEl, onLeft, onRight })
    metrics.js    ~200   NEW (v0.15.3) — session id + in-flight tracker + 50-entry buffer + sendBeacon flush to logClientMetrics on visibility-hidden. Exposes window.__apiStats / __apiStats_session / __apiStatsFlush() for Safari DevTools.
  views/
    categorize.js  ~560  Manual + Auto sub-tabs; calendar period bar at top; top-right Sync/Parse pill (v0.15 redesign)
    setup.js       ~100  underline-style config form + version list (v0.15 redesign)
    dashboard.js  ~320   calendar period bar; 4-col summary strip (Income / Fixed / Budgeted / Ready); collapsible +/- category groups; goal-linked categories suppressed and moved into the Goals section (v0.15.2); tap-to-expand goal cards
```

**Routes:** `#/categorize` (default), `#/dashboard`, `#/setup`. Navigation via `<a href="#/...">` in the bottom tab-bar (3 tabs since v0.15 — Settings is a tab now, not a header button).

**View contract:** every view module default-exports `{ mount(root), unmount() }`. `mount` renders into `#view-root` and attaches listeners. `unmount` is typically empty — in-view DOM is wiped by the router's `root.innerHTML = ''` before the next mount.

**Shell chrome (v0.15):** the `<header>` element is hidden via CSS. The period bar is the visual top of the app (on Categorize + Dashboard) and extends into the iOS safe area via `padding-top: calc(env(safe-area-inset-top, 0px) + 10px)` so the Dynamic Island notch is covered in the period bar's tan `#EFEDE8` background. Setup has no period bar and pads its own section. `viewport-fit=cover` on the viewport meta is required — without it `env(safe-area-inset-*)` returns 0 on iOS.

**Categorize chrome:** period bar at top (collapsible 7-day calendar grid, `‹ ›` chevrons for prev/next period), with `Sync N` (primary pill) or `↻ Parse` (outline pill) in the right slot. Manual | Auto segmented control directly beneath. Undo bar floats above the tab bar; toast at the top, safe-area-aware.

**Manual | Auto sub-tab:** segmented control inside the categorize view (not a sub-route), persisted in `localStorage.budget_categorize_subtab`. Manual tab = one tap → picker. Auto tab = rows where `suggest(merchant)?.confidence >= 0.70 && !rejectedThisSession.has(timestamp)`. Swipe right = accept, swipe left = hide for this session only. `rejectedThisSession` is intentionally in-memory — next session's richer index gets another chance.

**Dashboard (v0.15.2):** same period bar (`Day X of Y` in the right slot). 4-col summary. Main categories are `+`/`−` collapsible. **Categories whose `sub` is linked to a saving goal are filtered out** — they render only in the Goals section so the user doesn't see the same item twice. The filter is data-driven (`goal.linkedCategory` match), not a hardcoded "Savings" main name.

**Tab-bar (v0.12.2+):** bottom-fixed, always visible. Active tab has a thick top accent bar + warm-gray fill + uppercase bold label. Stacks at `var(--tab-bar-total) = 72px + env(safe-area-inset-bottom)`.

**Service worker (v24):** precaches the shell (`app.js`, `router.js`, `ui.js`, `config.js`, `api.js`, `store.js`, `periods.js`, `index.html`, `style.css`, `manifest.json`). Lazy view + lib modules under `/js/views/` and `/js/lib/` are served via stale-while-revalidate. `script.google.com` requests bypass the SW entirely (so `sendBeacon` flushes to the metrics endpoint aren't cached). Bump `CACHE_VERSION` on every PWA release.

**State:** `store.js` is still a singleton loaded once in the shell. No pub/sub — cross-view signaling is two explicit calls: `categorize.js` calls `invalidateDashboardCache()` + `invalidateSuggestIndex()` after successful `batchCategorize`. Two callers; revisit if it grows.

**Client metrics (v0.15.3):** `lib/metrics.js` wraps every request in `api.js`. Captured fields: sessionId, mountN, appVersion, connection, action, clientStartMs, clientTotalMs, serverMs (from `data._elapsedMs`), networkMs (total − server), inFlightAtStart, msSincePrev, duplicateDetected, cached, ok, errorMsg, bytes, note. The buffer flushes on `visibilitychange: hidden` + `pagehide` via `navigator.sendBeacon` (text/plain to skip CORS preflight — the Apps Script endpoint accepts either GET or POST JSON). The `logClientMetrics` action is excluded from its own instrumentation so it doesn't log about logging. Records land in the `ClientMetrics` tab with one `setValues` call per batch.

## Things that will trip you up (lessons from past sessions)

> ⚠️ **Before you assume "Budget miscalculation"**: the Available column is CUMULATIVE rollover, not "this period only". If a category overspends in any period, the negative balance carries forward forever via the prior-period SUMIFS. A row showing -$280 with $100 budgeted and $40 spent is the formula working correctly against an earlier overspend, not a bug. Trace the chain back through that category before assuming miscalculation. The user has been bitten by this twice (v10.4 circular-ref divergence + late v11.x Gas confusion). Redesign to a non-rollover or two-column model has been discussed but deferred — see `docs/findings.md` "Gas Rollover Investigation (non-bug)".

1. **`getLastRow()` lies on formula-filled sheets.** Transactions tab has formulas in rows 2–1000 that return `""`. `getLastRow()` reports 1000, not the real last data row. Always use `findNextEmptyRow_()` (scans column A) — already fixed in v9.

2. **POST body is lost on Apps Script 302 redirects.** Use GET with URL params for everything. `doGet()` routes all 6 actions; `doPost()` is kept for curl testing only.

3. **Plain `clasp deploy` creates a new URL.** Always use `./deploy.sh` or `clasp deploy -i AKfycbw2EbHNk_...`.

4. **The Apps Script editor and clasp can both edit Code.gs.** If the user makes an edit in the editor, run `clasp pull` BEFORE editing locally to avoid clobbering.

5. **Categories tab is named "Setup", not "Categories".** Categories live in Setup `D2:E100` (Main, Sub).

6. **PWA gating on Transactions tab is `Category="" AND Timestamp set`.** Empty Category = "uncategorized." Manual rows (blank Timestamp) are invisible to the PWA by design.

7. **API key is in Apps Script Script Properties** (set via Budget Tools → Set API Key menu). Never hardcoded.

8. **The user already manually pasted v9 to Apps Script** before clasp migration. The remote and local are in sync as of clasp clone.

9. **`Slicer.setColumnPosition()` throws TypeError in web-app context** (Google API change discovered Apr 2026). Slicer manipulation in `rebuildBudgetInternal_` is now wrapped in try/catch with a typeof guard, and prefers `setRange()` on the existing slicer instead of destroying-and-recreating. Don't reintroduce the destroy-then-recreate pattern. See `docs/findings.md` "Slicer.setColumnPosition API Change Bug (v11.7)".

10. **`setNamedRanges_` deletes-and-recreates ranges — any formula referencing them at deletion time is permanently broken to `#REF!`**. Recreating the same name with the same definition does NOT heal existing formulas. Therefore any code that writes formulas referencing named ranges (Saving tab builder is the current example) MUST run AFTER `setNamedRanges_` in `updateWorkbook`. See `docs/findings.md` "Saving Tab #REF! After Update Script (v11.9)".

11. **XLOOKUP with multiplied-boolean lookup arrays is unreliable in Sheets.** A formula like `XLOOKUP(1, (startCol<=today)*(endCol>=today), labelCol)` may return no-match even when a match clearly exists. Prefer `INDEX(labelCol, MATCH(today, startCol, 1))` when the start column is ascending-sorted — it's more portable and doesn't rely on array-broadcast behavior. See `docs/findings.md` "Saving B3 XLOOKUP Out-of-Range (v11.10)".

12. **updateWorkbook's in-place per-row setFormula refresh silently fails (v11.12).** The same setFormula text that works from `rebuildBudgetInternal_` stored `#REF!` when called from the in-place loop inside `updateWorkbook` — even when the named ranges existed (dashboard formulas in the same tab resolved correctly). Root cause unknown; suspected Apps Script state-commit quirk. Fix: `updateWorkbook` now calls `rebuildBudgetInternal_('refresh', ss)` instead of the per-row loop. Don't reintroduce per-row refresh in `updateWorkbook`. See `docs/findings.md` "Budget #REF! After updateWorkbook (v11.12)".

13. ~~**PWA views must declare `setHeaderActions` on mount.**~~ **OBSOLETE as of v0.12.2.** Refresh and Sync moved out of the shell header into the categorize view itself (inline `⟳` icon next to the period dropdown; sync bar sticky-bottom, visible only when `syncQueue.length > 0`). Header is now title + Settings only. `setHeaderActions` helper deleted. Don't reintroduce shell-level chrome that needs per-view declaration — the pattern was a mistake.

14. **In-view event listeners die with the DOM; shell-level listeners must be removed explicitly.** The router does `root.innerHTML = ''` before mounting the next view, so any listener on an element inside `#view-root` is garbage-collected. The only shell-level listener today is on `#settings-btn` — `app.js` handles it once at boot, so views don't need to clean up. If you add a new shell-level element that a view attaches listeners to, track the handler refs and remove them in `unmount()`.

15. **Merchant normalizer MUST produce identical keys for variants of the same merchant (v0.14).** The suggestion index aggregates by normalized merchant; if `AMAZON.COM*MT12345 SEATTLE WA` and `AMAZON.COM*XY98765 SEATTLE WA` normalize to different keys, the index bucketizes them separately and confidence stays below threshold forever. The normalizer uses `\*[a-z0-9]+` (strip card/txn suffixes anywhere), `#\w+` (strip store IDs), and `\S*\d+\S*` (strip any token containing digits — including hyphenated like `T-0384`). If you touch `normalizeMerchant()`, run the test block in the v0.14 commit message / session log against the full 17-case suite before shipping.

16. **iOS safe-area needs BOTH `viewport-fit=cover` AND `env(safe-area-inset-*)` (v0.15.1).** Without `viewport-fit=cover` in the viewport meta, `env(safe-area-inset-top)` silently returns `0` on iOS and you end up hardcoding pixel values that are wrong for iPhone 16 Pro's Dynamic Island (~62px inset) or any future device. Symptoms: a white/mismatched strip above your top bar on notched iPhones. Fix: the top visual component (period bar on Categorize + Dashboard, section wrapper on Setup) does `padding-top: calc(env(safe-area-inset-top, 0px) + <design offset>px)` and extends its own background into the notch area. Don't re-introduce a fixed `<header>` spacer.

17. **Floating top offsets (toasts, pickers) must also be safe-area-aware.** `#error-toast top: 64px` and `#category-picker top: 100px` were calibrated against the old fixed-header layout; on iPhone 16 Pro they hide under the Dynamic Island or overlap the period bar. Use `top: calc(env(safe-area-inset-top, 0px) + <offset>)` for anything anchored near the viewport top.

18. **Dashboard category / saving-goal duplication (v0.15.2).** "Savings" main category subs (Europe, NDEB, etc.) pulled double duty as both Budget category rows and Goal cards. Dashboard now filters `categoriesByPeriod` by `!goal.linkedCategory.has(sub)` so the same item never shows twice. The filter is data-driven — don't hardcode `main === 'Savings'` (future goals may live under different mains).

19. **Apps Script web-app POST must use `text/plain` (or GET) to avoid CORS preflight.** iOS Safari sends an `OPTIONS` preflight for any POST with `Content-Type: application/json`, and Apps Script responds with a 302 redirect that breaks preflight. The symptom is a silent fetch failure with no error reaching the client. `lib/metrics.js` uses `navigator.sendBeacon` with a `text/plain` Blob for exactly this reason; `doPost` parses `e.postData.contents` as JSON regardless of the declared content type.

20. **Instrumentation self-exclusion: the logger must never log about itself.** `lib/metrics.js` flushes to `logClientMetrics`, which is an Apps Script call like any other. `api.js` specifically skips instrumenting this endpoint (`metricKey !== 'logClientMetrics'` guard) — otherwise the act of reporting generates a report about reporting, and the buffer fills with recursive meta-noise. If you add a new diagnostic endpoint, apply the same guard.

21. **`_elapsedMs` is server-self-reported exec time, not total round-trip.** The `doGet`/`doPost` wrappers echo `_elapsedMs = Date.now() - start` on every response so the client can compute `networkMs = clientTotalMs - serverMs`. Do NOT treat it as a true network metric — it excludes Apps Script's cold-container spin-up (the infamous 2–3 s first-call tax) because that happens before the handler starts timing. In the `ClientMetrics` tab, a high `NetworkMs` with normal `ServerMs` signals cold-container or TLS/DNS cost, not slow script execution.

22. **GitHub Pages needs `.nojekyll` at the repo root.** Without it, Pages runs Jekyll by default. We observed a failure mode on Apr 23 2026 where the build step "succeeded" but the deploy step hung at `updating_pages` until timeout (`Error: Timeout reached, aborting!`). Adding `.nojekyll` (empty file) + an empty-commit retrigger cleared it. Don't delete the marker; it belongs on every branch Pages deploys from.

23. **Dashboard summary block reflects `Budget!B1` in the sheet, not the PWA's selected period.** `Net Income / Fixed Expenses / Ready to Assign` come from the pre-computed `A4:F4` row, which is period-aware via `$B$1`. Replicating them per-period client-side requires fetching Transactions + FixedMonthlyExpenses + Setup (3 more reads). v0.13 scope explicitly accepts this limitation. If the user complains, the fix path is a new `dashboardData` endpoint in Apps Script or the extra fetches in `lib/budget.js` — both are documented in the v0.13 plan's "non-goals."

24. **Concurrent `dumpSheet` requests must not duplicate.** `lib/suggest.js` dedups via a module-level `ensurePromise` — two simultaneous Auto-tab renders only trigger one network call. `lib/budget.js` is single-entrypoint (`getDashboardData`) so no dedup logic is needed there. If you add a third data-layer module, follow the `ensurePromise` pattern.

25. **Any PWA call fired from `mount()` AND awaited inside `refresh()` causes a duplicate roundtrip (v0.15.4).** ClientMetrics confirmed `fetchCategories` was firing twice per mount — once background from `mount()`, once awaited inside `refresh()` — paying the ~2.5s Apps Script network tax twice. The bug class is "two entry points, both want the same data, neither knows about the other." Fix: store the mount's promise in a module variable (`categoriesPromise`) and have `refresh()` await it instead of firing a second identical call. User-initiated refreshes (Parse pill + empty-state Refresh button) opt into a fresh fetch via `refresh({ force: true })`. If you ever add a third entry point, share the promise too. See `docs/findings.md` "Cold-Start Perf Findings + Fix (v0.15.4)".

26. **PWA view re-mounts are not free — `await refresh()` on every mount pays the full cold tax.** Navigating Categorize → Dashboard → Categorize triggers a router re-mount that re-fires all awaited API calls. With each call paying ~2.5s of network overhead regardless of container warmth, re-mounts previously cost 6-9s every time. Fix in `views/categorize.js`: `refresh()` takes `{ force: false }` by default and no-ops if the last successful run was <60s ago AND didInitialRefresh is true. User-initiated Parse always bypasses the throttle. See `docs/findings.md` "Cold-Start Perf Findings + Fix (v0.15.4)".

27. **Apps Script Triggers panel doesn't auto-refresh after programmatic install.** `installEmailTrigger` (v11.16) creates a time-based trigger via `ScriptApp.newTrigger(...).create()`. The trigger IS installed and starts firing on schedule, but the editor's left-sidebar Triggers panel can show empty state for an open editor tab from before the install. **Fix:** hard-reload the editor tab (Cmd+Shift+R), or close-and-reopen. Verifying programmatically — running `ScriptApp.getProjectTriggers()` from the editor — gives the truth regardless. The trip-up: trusting the UI panel without a reload led to a "Phase 1 broken" false alarm on 2026-04-28 that was actually a stale tab.

28. **Running a trigger handler from the editor's Run button does NOT install a trigger.** A common confusion when bringing up time-driven triggers: clicking Run on `processInfoAlertsTrigger` from the function dropdown only executes the handler once (which IS useful for forcing a permissions re-grant on new scopes). The trigger itself is created by `installEmailTrigger` — call this from the menu (Budget Tools → Setup Email Trigger) OR run it once from the editor too. Symptom of the confusion: a `triggerParseEmails` row appears in Logs but no trigger shows in the Triggers panel — because the *handler* ran, not the *installer*. See `docs/findings.md` "Time-Driven Email Parsing (v11.16 → v11.17)".

29. **Archiving a savings goal is now a one-shot action — don't just check Setup col F.** Pre-v11.18 behavior was: ticking Setup col F (Archived?) hid a sub-category from the PWA dropdown but left it in the Budget tab forever. v11.18 changed this: `rebuildBudgetInternal_` now filters Setup col F, AND there's a dedicated `Budget Tools → Archive Goal...` menu that does all three things atomically (set Saving col J = Achieved, flip Setup col F if no other goals depend on it, force Budget rebuild). Trip-up: just checking col F by hand still works (PWA hides it, next rebuild drops it from Budget) but the Saving tab status doesn't auto-update — leaves the tabs visually inconsistent (Saving says Active, Setup says archived). Use the menu for atomicity. Trade-off: budgeted values for archived sub-categories in past periods are lost on rebuild — disclosed in the menu's confirmation prompt. See `docs/findings.md` "Goal Archive Flow (v11.18)".

30. **Project-scoped skills register at SESSION START, not mid-session.** Skills under `.claude/skills/` are auto-discovered when Claude Code begins a session in this repo. If a skill is added or updated mid-session via `git pull`, `git merge`, or branch switch, the running Claude session won't see it — `Skill('skill-name')` returns "Unknown skill". The actual SKILL.md file works the same; only the registration needs a fresh session. **Workaround:** read the SKILL.md directly and follow the workflow manually (the same pattern works as the registered invocation). The `update-budget-docs` skill documents this in its own SKILL.md "Known limitation" section. The four current skills are: `update-budget-docs`, `state`, `lint`, `deploy`. See `docs/findings.md` "Claude Code Workflow Tooling".

31. **The `pwa/pixel-ui-redesign` branch is force-pixel; no theme toggle in Settings.** If you cold-open the PWA on this branch, the early `<head>` script in `index.html` hardcodes `data-theme="pixel"` before any CSS parses. There's no in-app way to switch back to mono — the toggle UI was removed in v0.19.1 after on-device feedback that mono had drifted on the branch (the multi-select rail, period bar today chip, etc. were designed for pixel; mono variants felt out of place). To revert visually: switch GitHub Pages source back to `main`, OR check out a pre-pixel commit, OR revert the v0.19.1 commit which restores the toggle. Mono CSS in `style.css` stays as the structural foundation pixel.css overrides — bringing the toggle back is a single-commit revert. See `docs/findings.md` "Pixel UI Theme System (PWA v0.18.0 → v0.19.1)".

32. **Budget tab schema changes break the PWA dashboard parser if not paired.** The PWA's `parseDashboard` (in `js/lib/budget.js`) reads Budget tab columns by INDEX — `row[5]` for Available pre-v11.19, `row[6]` after. Adding/removing/reordering Budget tab columns requires a paired PWA parser update OR the dashboard cards silently show WRONG numbers (no error toast — just values from the wrong column). v11.19 added "Rolled Over" between Spent and Available, shifting Available F → G; PWA pre-v0.19.3 still reads col F. **Pattern to follow:** any time `rebuildBudgetInternal_`'s column count changes in `apps-script/Code.js`, search for `parseDashboard` in `js/lib/budget.js` and update the `row[N]` indices. Bonus: `Budget_*` named ranges in `setNamedRanges_` shift correspondingly — Saving tab + dashboard formulas use named ranges and survive transparently, but PWA reads raw arrays from `dumpSheet` and DOESN'T benefit from named-range indirection. Check both layers when changing column count. See `docs/findings.md` "Budget Tab Schema Evolution (v11.19)".
